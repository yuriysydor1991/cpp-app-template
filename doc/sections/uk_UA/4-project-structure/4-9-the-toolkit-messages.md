## Повідомлення інструментарію

Програма веде журнал за допомогою макросів з `src/log/log.h`, тоді як GTK, GDK, GIO, Pango, gtkmm і сам GLib звітують через журналювання GLib, яке своїм типовим записувачем пише у стандартні потоки виводу і помилок процесу. Тож без додаткових заходів скаргу інструментарію бачить лише той, хто дивиться у термінал, і більше ніхто - вона ніколи не потрапляє у файл журналу, не має ані відмітки часу у форматі програми, ані ідентифікатора потоку, і не зважає на жодне налаштування рівня журналювання програми.

Клас `Gtkmm3i::gtklog::GtkLogBridge` з каталогу `src/gtkmm3/log` перебирає це на себе. Його метод `install`, що викликається на самому початку `Gtkmm3i::GtkmmIniter::run`, ще до того як буде задіяно будь-що з інструментарію, встановлює три речі:

- власний записувач GLib замість типового, який перетворює кожен набір полів повідомлення на виклик макросів журналювання програми;
- обробник `g_print`, який записує надрукований текст з рівнем info;
- обробник `g_printerr`, який записує його з рівнем warning.

Рівні GLib відображаються таким чином:

| Рівень GLib | Рівень програми |
| --- | --- |
| `G_LOG_LEVEL_ERROR` | error |
| `G_LOG_LEVEL_CRITICAL` | error |
| `G_LOG_LEVEL_WARNING` | warning |
| `G_LOG_LEVEL_MESSAGE` | info |
| `G_LOG_LEVEL_INFO` | info |
| `G_LOG_LEVEL_DEBUG` | debug |
| будь-що інше | info |

Рівні error і critical у GLib обидва означають порушений інваріант, тому обидва тут є помилками. Бібліотека вільна оголошувати власні рівні понад рівні GLib, і ті не несуть жодної відомої програмі важливості, тож вони записуються у журнал і ніколи не відкидаються.

GTK побудовано зі структурованим журналюванням, тож його повідомлення називають файл, рядок і функцію вихідного коду інструментарію, звідки вони походять, і рядок журналу несе усі три з них. Сам GLib звітує про більшість власних негараздів старішим шляхом, який не несе таких полів, і тоді на початку повідомлення стоїть лише домен:

```
... DBG ... GtkLogBridge.cpp:157 : Gtk: gtkiconpaintable.c:365: gtk_icon_paintable_snapshot_with_weight: snapshot symbolic icon as recolored node
... DBG ... GtkLogBridge.cpp:157 : GLib-GIO: _g_io_module_get_default: Found default implementation local (GLocalVfs) for ‘gio-vfs’
... WRN ... GtkLogBridge.cpp:154 : Gtk: gtkmain.c:738: gtk_init: Failed to open display
```

Міст веде журнал через макроси `LOG*`, а не через клас логера напряму, тож він продовжує працювати на гілках, які замінюють усю реалізацію журналювання (`appLog4Cpp5`, `appBoostLog`). Платою за це є координати джерела рядка журналу: вони називають сам файл `GtkLogBridge.cpp`, тоді як координати інструментарію стоять всередині тексту повідомлення.

### Що взагалі потрапляє у журнал

Перед файлом журналу стоять два фільтри, і міст зберігає обидва.

Перший з них - власний фільтр інструментарію: повідомлення рівнів info і debug потрапляють у журнал лише тоді, коли їхній домен увімкнено змінною середовища `G_MESSAGES_DEBUG`, точно так само, як це вирішує типовий записувач GLib:

```bash
G_MESSAGES_DEBUG=all ./YourApplication
```

Без цієї змінної попередження, критичні повідомлення і помилки все одно потрапляють у журнал - поза ним залишається лише балаканина внутрішньої кухні інструментарію. Така поведінка притаманна кожній програмі на GTK, і заміна записувача не повинна її змінювати.

Другий фільтр - це `MAX_LOG_LEVEL` побудови, той самий, якому підкоряються власні повідомлення програми. Побудова, яка називає рівень info своїм найвищим (типове `-DMAX_LOG_LEVEL=3`), відкидає повідомлення інструментарію рівня debug, що б не казала змінна `G_MESSAGES_DEBUG`, і навіть не збирає їхній текст.

### Правило одного записувача на процес

GLib приймає записувач журналу лише один раз за життя процесу і вбиває процес при другому виклику `g_log_set_writer_func`, тому міст встановлює себе один раз і ігнорує кожен наступний виклик. Збережи це єдине місце за ним: оскільки записувач діє на увесь процес, він і так перехоплює повідомлення GLib від кожної бібліотеки у складі виконуваного файлу, включно з GStreamer і WebKitGTK.
