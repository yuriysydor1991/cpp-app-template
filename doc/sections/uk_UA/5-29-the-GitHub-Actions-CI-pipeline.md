## Конвеєр CI GitHub Actions

Робочий процес [.github/workflows/ci.yml](/.github/workflows/ci.yml) повторює стадії побудови, тестування та перевірки коду конвеєра [misc/Jenkinsfile](/misc/Jenkinsfile) у [GitHub Actions](https://docs.github.com/en/actions), отож відгалуження проекту отримує ті самі перевірки без власного примірника [Jenkins](https://www.jenkins.io/). Вмикати для цього нічого не потрібно: робочий процес запускається на кожен push та на кожен pull request, а також вручну зі сторінки *Actions* сховища.

Його завдання виконуються паралельно, кожне на власному виконавці:

| Завдання | Що виконує |
| --- | --- |
| `Code format (clang-format)` | конфігурує з `-DENABLE_CLANGFORMAT=true`, будує ціль `clang-format` і завершується помилкою, коли форматувальник змінив хоч один відстежуваний файл |
| `Debug build & tests` | конфігурує тип побудови debug із санітайзерами, юніт- та компонентними тестами, будує її та запускає `meson test` |
| `clang-tidy` | конфігурує тип побудови debug з `-DENABLE_CLANG_TIDY=true` і будує ціль `clang-tidy` |
| `Release build & install` | будує тип побудови release та встановлює його до каталогу призначення всередині каталогу побудови |

Кожен тест гілки є окремим набором, отож єдиний запуск `meson test` покриває і юніт-, і компонентні тести. Він записує звіти JUnit XML до каталогу `meson-logs` дерева побудови, які завдання вивантажує як артефакт `junit-results` запуску, тож невдалий тест видно на сторінці запуску без читання журналів. Новий push до гілки скасовує ще не завершений конвеєр її попереднього коміту - про це дбає група `concurrency` робочого процесу.

### Виконавець та залежності гілки

Завдання виконуються на закріпленому виконавці `ubuntu-26.04`, а не на рухомому `ubuntu-latest`, який самостійно переходить до наступного LTS-випуску, тоді як потрібні гілці пакунки різняться між випусками. [Образ виконавця](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2604-Readme.md) вже містить компілятори та інструменти clang, отож завдання додає решту єдиним рядком `apt-get install`, а серед неї - і змінну `DEPENDENCIES` робочого процесу:

```
env:
  BUILDDIR: build
  # The development packages of the branch specific libraries.
  DEPENDENCIES: ''
```

Саме ця змінна - єдиний рядок, яким різняться гілки шаблону, отож проект, який долучає власну бібліотеку, дописує туди її пакунок розробки. Ця гілка не потребує пакунків, яких бракує образу виконавця, отож її власний рядок лишається порожнім.

### Параметри ручного запуску

Кнопка *Run workflow* сторінки *Actions* запускає конвеєр з параметрами, що віддзеркалюють параметри [misc/Jenkinsfile](/misc/Jenkinsfile):

| Параметр | Відповідник у Jenkins | Що запускає |
| --- | --- | --- |
| `run_cppcheck` | `RUN_CPPCHECK` | побудову цілі `cppcheck` у завданні Debug |

Типово вимкнений, оскільки перевірка коштує хвилин часу виконавця, за які платив би кожен push.

### Що лишається конвеєру Jenkins

Перевірки шаблону з [misc/Jenkinsfile](/misc/Jenkinsfile) - розділи документації та їхні посилання у README, посилання markdown, зовнішні URL документації, зареєстровані enabler-модулі та зареєстровані тести - не мають тут відповідника, як і його перевірки пакувальників: робочий процес обмежується стадіями, які покриває звичайний виконавець, тоді як пакувальники потребують середовищ виконання та інструментів, які містить [контейнер конвеєра Jenkins](/doc/sections/uk_UA/5-17-enabling-Jenkins-pipeline-inside-Docker-container.md).
