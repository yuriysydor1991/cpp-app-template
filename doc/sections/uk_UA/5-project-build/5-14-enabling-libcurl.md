## Вмикання інтеграції libcurl

Підтримку [libcurl](https://uk.wikipedia.org/wiki/CURL) для проекту вмикає CMake змінна `ENABLE_LIBCURL`, яка на цій гілці має значення `ON` за замовчуванням. Якщо бібліотека встановлена в системі, використовується саме вона, інакше через наявне з'єднання завантажуються та збираються сирці релізу `TEMPLATE_APP_CURL_GIT_TAG` (за замовчуванням `curl-8_23_0`).

```
# в середині кореневої директорії проекту

cmake -S . -B build -DENABLE_LIBCURL=ON
```

Клієнт ChatGPT цієї гілки надсилає свої запити саме за допомогою libcurl, тож тут ця опція є обов'язковою: крок конфігурування CMake завершується з пояснювальним повідомленням, якщо опцію вимкнути (`OFF`).

### Запити, які виконує CURLController

Клас `curli::CURLController` з директорії `src/CURL` утримує один easy-дескриптор libcurl і виконує з його допомогою запити:

| Виклик | Запит |
| --- | --- |
| `download(url)` | GET-запит, що завантажує тіло відповіді заданої URL |
| `download(url, headers)` | той самий GET-запит із додатковими заголовками, кожен з яких має форму `Назва: значення` (наприклад, авторизаційний) |
| `post(url, body, headers)` | POST-запит, що надсилає задане тіло разом із додатковими заголовками |
| `is_url_alive(url)` | HEAD-запит, що перевіряє досяжність URL без завантаження її тіла |
| `last_response_successful()` | повідомляє, чи відповіли на останній виконаний запит успішним статусом |
| `last_response_code()` | код HTTP-статусу останнього виконаного запиту |
| `get()` | буфер із тілом відповіді, отриманим останнім запитом |

Кожен виклик відкидає тіло, отримане попереднім, і скидає опції дескриптора, тому завантаження, виконане після відправлення post-запиту, не успадковує ані його метод, ані його тіло і заголовки. Отримане тіло повертається як посилання на `std::vector<char>`, який лишається порожнім у разі будь-якої помилки.

Про результат запитуй метод `last_response_successful`, а не порівнюй значення `last_response_code` із власною сталою статусу, що тримає HTTP-статуси всередині контролера. Причиною є протоколи без кодів: файлова передача повідомляє нульовий код відповіді і коли вдається, і коли зазнає невдачі, тож сам лише код ніяк не відрізняє одне від одного, а відповідь із перенаправленням теж не вважається успіхом. Значення `last_response_code` лишається для повідомлень і для коду, якому справді потрібен власний статус:

```cpp
#include <string>

#include "src/CURL/CURLController.h"

auto curl = curli::CURLController::create();

if (!curl->is_url_alive("https://example.com/api/")) {
  return;
}

const auto& answer =
    curl->post("https://example.com/api/", R"({"ask":"something"})",
               {"content-type: application/json",
                "authorization: Bearer a-token-of-yours"});

if (!curl->last_response_successful()) {
  // запит не вдався або сервер повідомив помилковий статус, точне значення
  // якого дає метод last_response_code
}

const std::string received{answer.begin(), answer.end()};
```

Відповідь із перенаправленням вважається ознакою досяжності і не переслідується, натомість сервер, що відхиляє сам метод HEAD (наприклад, зі статусом `405`), повідомляється як недосяжний, тому таку URL перевіряй завантаженням.

Завантаження припиняється після `DEFAULT_TIMEOUT` секунд, а застряглу передачу обриває навіть раніше (менше ніж `DEFAULT_LOWSPEEDLIMIT` байтів на секунду протягом `DEFAULT_LOWSPEEDSECS` секунд). Post-запит взагалі не застосовує обриву за низькою швидкістю і натомість очікує `DEFAULT_POST_TIMEOUT` секунд, бо сервер, що складає відповідь, тим часом нічого не надсилає у з'єднання. Усі ці значення є полями класу, які слід змінити під потреби твоїх запитів.

### Тестування контролера

Клас покривають два тестові виконувані файли з директорії `src/CURL/tests`, і жоден з них не виконує жодного мережевого обміну:

- `UTEST_CURLController` — юніт-тест викликів, які завершуються ще до початку будь-якої передачі, як-от із порожньою URL або з непідтримуваним протоколом. Вмикається CMake змінною [ENABLE_UNIT_TESTS](/doc/sections/uk_UA/5-project-build/testing/5-3-1-enabling-unit-testing.md).
- `CTEST_CURLController` — компонентний тест, який задіює справжню libcurl через файловий протокол на файлах, що їх сам записує до власної директорії побудови. Вмикається CMake змінною `ENABLE_COMPONENT_TESTS`.

Натомість код, що використовує контролер, тестується з його gmock-замінником із директорії `src/app/tests/mocks/CURLController`, яку цілі `UTEST_Application` та `CTEST_app` підключають перед справжнім заголовком. Розширюючи клас, тримай цей замінник у синхронізованому з ним стані.
