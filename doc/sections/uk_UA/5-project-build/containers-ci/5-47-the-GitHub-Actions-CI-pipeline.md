## Конвеєр CI GitHub Actions

Робочий процес [.github/workflows/ci.yml](/.github/workflows/ci.yml) повторює стадії побудови, тестування та перевірки коду конвеєра [misc/Jenkinsfile](/misc/Jenkinsfile) у [GitHub Actions](https://docs.github.com/en/actions), отож відгалуження проекту отримує ті самі перевірки без власного примірника [Jenkins](https://www.jenkins.io/). Вмикати для цього нічого не потрібно: робочий процес запускається на кожен push та на кожен pull request, а також вручну зі сторінки *Actions* сховища.

Його завдання виконуються паралельно, кожне на власному виконавці:

| Завдання | Що виконує |
| --- | --- |
| `Code format (clang-format)` | конфігурує з `-DENABLE_CLANGFORMAT=ON`, будує ціль `clang-format` і завершується помилкою, коли форматувальник змінив хоч один відстежуваний файл |
| `Debug build & tests` | конфігурує побудову Debug із санітайзерами, юніт- та компонентними тестами, будує її та запускає набори `UTEST_` та `CTEST_` через `ctest` |
| `clang-tidy` | конфігурує з `-DENABLE_CLANG_TIDY=ON` і будує, отож перевірки виконуються під час компіляції |
| `Release build & install` | будує конфігурацію Release та встановлює її до префіксу всередині каталогу побудови |

Кожен запуск `ctest` записує звіт JUnit XML, який завдання вивантажує як артефакт `junit-results` запуску, тож невдалий тест видно на сторінці запуску без читання журналів. Новий push до гілки скасовує ще не завершений конвеєр її попереднього коміту - про це дбає група `concurrency` робочого процесу.

### Виконавець та залежності гілки

Завдання виконуються на закріпленому виконавці `ubuntu-26.04`, а не на рухомому `ubuntu-latest`, який самостійно переходить до наступного LTS-випуску, тоді як потрібні гілці пакунки різняться між випусками. [Образ виконавця](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2604-Readme.md) вже містить компілятори та інструменти clang, отож завдання додає решту єдиним рядком `apt-get install`, а серед неї - і змінну `DEPENDENCIES` робочого процесу:

```
env:
  BUILDDIR: build
  BDJUNITOUT: junit-out
  # The development packages of the branch specific libraries.
  DEPENDENCIES: freeglut3-dev libglew-dev libxi-dev
```

Саме ця змінна - єдиний рядок, яким різняться гілки шаблону, отож проект, який долучає власну бібліотеку, дописує туди її пакунок розробки.

### Параметри ручного запуску

Кнопка *Run workflow* сторінки *Actions* запускає конвеєр з параметрами, що віддзеркалюють параметри [misc/Jenkinsfile](/misc/Jenkinsfile):

| Параметр | Відповідник у Jenkins | Що запускає |
| --- | --- | --- |
| `run_cppcheck` | `RUN_CPPCHECK` | побудову цілі `cppcheck` у завданні Debug |

Типово вимкнений, оскільки перевірка коштує хвилин часу виконавця, за які платив би кожен push.

### Що лишається конвеєру Jenkins

Перевірки шаблону з [misc/Jenkinsfile](/misc/Jenkinsfile) - розділи документації та їхні посилання у README, посилання markdown, зовнішні URL документації, зареєстровані enabler-модулі та зареєстровані тести - не мають тут відповідника, як і його перевірки пакувальників: робочий процес обмежується стадіями, які покриває звичайний виконавець, тоді як пакувальники потребують середовищ виконання та інструментів, які містить [контейнер конвеєра Jenkins](/doc/sections/uk_UA/5-project-build/containers-ci/5-17-enabling-Jenkins-pipeline-inside-Docker-container.md).
