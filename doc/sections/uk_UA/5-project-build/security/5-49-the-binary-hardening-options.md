## Параметри захисту (hardening) бінарних файлів

Шаблон захищає кожен бінарний файл, який будує, отож вмикати для цього нічого не потрібно. Параметри відповідають [Compiler Options Hardening Guide for C and C++](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html) від OpenSSF і містяться у модулях каталогу [cmake/compile-options/hardening](/cmake/compile-options/hardening), які дописують їх до змінних `EXTRA_COMPILE_OPTIONS` та `EXTRA_LINK_OPTIONS`, що [src/CMakeLists.txt](/src/CMakeLists.txt) передає командам `add_compile_options` та `add_link_options`. Обидві змінні друкуються під час конфігурування, отож перелік узятих побудовою параметрів видно без читання рядків запуску компілятора:

```
-- COMPILE OPTIONS: -Wall;-Wextra;...;-fstack-protector-all;...
-- LINK OPTIONS: -Wl,-z,relro;-Wl,-z,now;-Wl,-z,noexecstack;...
```

### Параметри компіляції GCC та clang

| Параметр | Що виконує |
| --- | --- |
| `-fstack-protector-all` | розміщує "канарку" у кадрі кожної функції, а не лише тих, що містять масив, отож переповнення буфера на стеку виявляється до використання перезаписаної адреси повернення |
| `-fstack-clash-protection` | кожне виділення пам'яті на стеку торкається своєї сторінки-вартового, отож велика локальна змінна не може перестрибнути її до іншої ділянки пам'яті |
| `-fcf-protection=full` | відстеження непрямих переходів і тіньовий стек технології забезпечення потоку керування x86 (CET) |
| `-mbranch-protection=standard` | відповідник для AArch64: ідентифікація цілей переходів і підписування адрес повернення |
| `-fzero-call-used-regs=used-gpr` | очищує використані регістри загального призначення під час повернення, що вкорочує гаджети, з яких будується атака на зворотних переходах (ROP) |
| `-fstrict-flex-arrays=3` | лише кінцевий член `[]` є гнучким масивом, отож члени `[0]` та `[1]` зберігають відомий перевіркам меж розмір |
| `-fno-delete-null-pointer-checks` | перевірки нульових вказівників коду переживають оптимізацію |
| `-fno-strict-overflow` | переповнення знакового числа згортається замість того, щоб бути невизначеною поведінкою, якою оптимізатор користується, прибираючи перевірки переповнення |
| `-fno-common` | двічі визначена змінна стає помилкою компонування замість мовчазного поділу пам'яті |
| `-D_GLIBCXX_ASSERTIONS` | вмикає перевірки передумов контейнерів та ітераторів libstdc++, зокрема меж `operator[]` |
| `-U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=3` | перевірки переповнення буферів у викликах бібліотеки C; скасування визначення йде першим, оскільки дистрибутив, який захищає типово, повідомив би про перевизначення макроса |
| `-ftrivial-auto-var-init=zero` | автоматичні змінні починаються з нулів, отож пропущена ініціалізація не читає залишків старого вмісту стеку |

Компіляційні відповідники `-fPIE` та `-fPIC` параметра компонувальника `-pie` походять зі змінної `CMAKE_POSITION_INDEPENDENT_CODE` модуля [template-project-compile-options](/cmake/compile-options/template-project-compile-options.cmake). Детальний опис самих параметрів міститься у документації [GCC instrumentation options](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html).

### Параметри компонування GCC та clang

| Параметр | Що виконує |
| --- | --- |
| `-Wl,-z,relro` | переміщення стають доступними лише для читання, щойно динамічний компонувальник їх розв'язав |
| `-Wl,-z,now` | усі символи розв'язуються під час запуску, чого потребує попередній параметр, щоб покрити і таблицю глобальних зміщень (повний RELRO) |
| `-Wl,-z,noexecstack` | позначає пам'ять стеку як невиконувану |
| `-Wl,-z,separate-code` | код і дані ніколи не поділяють сторінку пам'яті, отож сторінка даних не містить виконуваних залишків |
| `-pie` | позиційно незалежний виконуваний файл, що дозволяє рандомізації адресного простору переміщувати і код самого бінарного файлу |

Параметр `-pie` надається лише виконуваним файлам, оскільки компонувальник відхиляє його разом із `-shared` спільної бібліотеки. Решту з них описує документація [GNU ld options](https://sourceware.org/binutils/docs/ld/Options.html).

### Параметри для MS Windows (MSVC)

| Параметр | Що виконує |
| --- | --- |
| `/GS` | перевірка безпеки буфера: кука захищає адресу повернення функції, що містить буфер |
| `/guard:cf` | захист потоку керування: непрямий виклик перевіряється за таблицею дозволених цілей |
| `/Qspectre` | пом'якшення атак спекулятивного виконання класу CVE-2017-5753 |
| `/GUARD:CF` | відповідник `/guard:cf` для компонувальника |
| `/DYNAMICBASE` | образ придатний до переміщення, отож рандомізація адресного простору його пересуває |
| `/NXCOMPAT` | увімкнено запобігання виконанню даних (DEP) |
| `/HIGHENTROPYVA` | 64-бітова рандомізація адресного простору образу |
| `/CETCOMPAT` | позначає образ як сумісний із тіньовим стеком |

Детальний опис міститься у документації [MSVC compiler options](https://learn.microsoft.com/en-us/cpp/build/reference/compiler-options-listed-by-category?view=msvc-170) та [MSVC linker options](https://learn.microsoft.com/en-us/cpp/build/reference/linker-options?view=msvc-170). Набір інструментів MSVC лише попереджає про невідомий йому параметр (попередження `D9002` та `LNK4044`), отож старіший або не-x86 набір відкидає те, чого не має, замість припиняти побудову.

### Непідтримувані параметри відкидаються

Набори інструментів GCC та clang відхиляють невідомий їм параметр, а параметри захисту залежать від версії компілятора, компонувальника та цільового процесора: `-fcf-protection=full` належить процесорам x86, `-mbranch-protection=standard` - AArch64, а родина `-Wl,-z,*` - компонувальникам ELF. Тому кожен параметр наведених вище таблиць перед використанням перевіряється компіляцією та компонуванням крихітного джерельного файлу, а відхилений відкидається замість того, щоб зламати побудову. Перевірку виконують функції `template_project_check_supported_options` та `template_project_append_supported_option` модуля [cmake/tools/template-project-supported-options-function.cmake](/cmake/tools/template-project-supported-options-function.cmake), а конфігурування звітує про кожну з них:

```
-- Performing Test TEMPLATE_PROJECT_ACCEPTS__fcf_protection_full - Success
-- Performing Test TEMPLATE_PROJECT_ACCEPTS__mbranch_protection_standard - Failed
```

### Побудова Debug зберігає свою діагностику

Параметри `-D_FORTIFY_SOURCE` та `-ftrivial-auto-var-init=zero` надаються лише конфігураціям `Release`, `RelWithDebInfo` та `MinSizeRel`. Бібліотека C однаково ігнорує перший без оптимізації, тоді як другий приховував би читання неініціалізованої пам'яті від valgrind та санітайзерів, які запускає побудова Debug.

Побудова із санітайзерами навмисно знижує захист потоку керування та вимикає захист від зіткнення стеку, отож параметри `-fcf-protection=full` і `-fstack-clash-protection` оминають її, а вибір генерації коду лишається за нею.

### Перевірка результату

Програма `readelf` з binutils повідомляє, що саме отримав побудований бінарний файл. Змінна `BINARY` містить шлях до нього (`build/src/CppAppTemplate` для типового дерева побудови):

```
# позиційно незалежний виконуваний файл: Type: DYN
readelf -hW "$BINARY" | grep Type

# повний RELRO: сегмент GNU_RELRO разом із прапорцем BIND_NOW
readelf -lW "$BINARY" | grep GNU_RELRO
readelf -dW "$BINARY" | grep BIND_NOW

# невиконуваний стек: прапорці RW, а не RWE, у GNU_STACK
readelf -lW "$BINARY" | grep -A1 GNU_STACK

# забезпечення потоку керування: можливості x86 IBT та SHSTK
readelf -nW "$BINARY" | grep "x86 feature"
```
